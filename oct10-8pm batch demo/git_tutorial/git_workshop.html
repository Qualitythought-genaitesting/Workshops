Day 1
Foundations
Understanding what version control is and why it matters
📂
Version Control
The foundation of every modern software project
What?

A system that records changes to files over time so you can recall specific versions later.

Why?

Mistakes happen. Version control lets you go back to any previous state of your project — like an infinite undo button.

When?

Every single time you work on any project — solo or with a team. Even for your personal portfolio.

Real World

Professional developers at Google, Netflix, and Apple all use version control. It's non-negotiable.

Problems Without Version Control

Think about the last time you worked on an assignment. Did you ever save it as final.html, final2.html, final_ACTUAL.html? That's the problem.
😰 Without Version Control
  • Files named project_v3_FINAL_2.html
  • Can't undo a mistake from 2 days ago
  • Sending files via WhatsApp to teammates
  • Two people editing the same file = chaos
  • No idea who changed what and when
✅ With Version Control
  • One clean folder, with full history
  • Undo any change from any point in time
  • Everyone works together seamlessly
  • See exactly who changed what and why
  • Roll back a bug instantly
🎮
Game Save Points: Imagine playing a game without being able to save. If you lose, you start from scratch. Version control is like a game that lets you save at any moment — and jump back to any save whenever you want.
✅
Summary Version control = a time machine for your code. It tracks every change, lets you go back in time, and helps teams work together without stepping on each other's toes.
⚙️
What is Git?
The version control software that runs on your computer
What?

Git is a free, open-source version control system created by Linus Torvalds (creator of Linux) in 2005.

Why?

It tracks every change you make to every file, who made the change, and when — automatically.

When?

Git runs on your computer. You use it whenever you want to save a "version" of your project.

Real World

The Linux kernel, the Android OS, the VS Code editor — all built using Git. 97% of developers use Git.

🎮
Git = Save Points in a game. Every time you "commit" in Git, it's like saving your game. You can always come back to any save point. You can have thousands of saves and switch between them instantly.

Key things Git does:

Tracks file changes Saves project history Manages multiple versions Enables teamwork Works offline
Git is software that lives on your computer. It does not require internet to work. GitHub (different thing!) adds the internet part.
✅
Summary Git = a tool installed on your computer that saves the history of your code. Think of it as an invisible time-stamping machine that watches your project folder.
🌐
What is GitHub?
Where your code lives online — the cloud home for Git projects
What?

GitHub is a website (github.com) that hosts Git repositories online so you and your team can access them from anywhere.

Why?

Your local Git history stays on your computer only. GitHub puts it in the cloud — backed up, shareable, and accessible from any device.

When?

When you want to back up your project, share with a team, show your work to employers, or deploy a website.

Real World

GitHub has 100+ million developers. Your portfolio on GitHub IS your professional identity in the tech world.

☁️
GitHub = Google Drive, but for code. Just like Google Drive stores your documents in the cloud, GitHub stores your code projects. But unlike Drive, it keeps the full history of every change ever made.

Git vs GitHub — Not the Same!

⚙️ Git
  • Software on your computer
  • Works offline
  • Tracks changes locally
  • Command-line tool
  • Created by Linus Torvalds
🌐 GitHub
  • Website on the internet
  • Requires internet connection
  • Stores code in the cloud
  • Has a visual interface
  • Owned by Microsoft
✅
Summary Git is the tool, GitHub is the platform. You use Git to track changes, then use GitHub to share those changes with the world. You can use Git without GitHub, but most people use both together.
🖥️
GitHub Desktop
A visual, beginner-friendly way to use Git
What?

GitHub Desktop is a free app that gives you a visual interface to use Git — no command line needed.

Why?

Git's command line can feel scary for beginners. GitHub Desktop shows everything visually with buttons and clear panels.

When?

Perfect when you're learning. Many professionals also use it for day-to-day work. Download at desktop.github.com.

Real World

Designers, junior devs, project managers — anyone who wants to use Git without memorizing commands.

🚗
GitHub Desktop = Automatic car. Git CLI = Manual car. Both get you to the same destination. The automatic car is easier to start with — you focus on driving, not the gear changes. Once you understand how it works, you can learn manual (the command line) for more control.
🖥️ GitHub Desktop (Automatic)
  • Visual buttons for every action
  • See your changes highlighted in color
  • Click to commit, push, pull
  • Easy for beginners
  • Great for seeing history visually
⌨️ Git CLI (Manual)
  • Type commands in Terminal
  • More powerful and flexible
  • Faster once you know the commands
  • Works on any server or environment
  • Industry standard for professionals
✅
Summary GitHub Desktop is a friendly app that wraps Git in a nice interface. Perfect for beginners. We'll use it in Day 2, then graduate to the command line in Day 3.
📁
Repository
The project folder that Git tracks
What?

A repository (repo) is a folder for your project that Git tracks. It contains all your files AND the complete history of every change.

Why?

Instead of multiple "final2" copies, you have one folder with the entire history hidden inside a .git folder.

When?

Every project gets its own repository. Starting a new website? Create a new repo. Starting a new app? Create a new repo.

Real World

The VS Code editor is one giant repository on GitHub with 300,000+ commits (saves) from 1,000+ contributors.

📓
Repository = A magic project folder. It looks like a regular folder, but Git is silently watching everything inside it. Every file you add, change, or delete is recorded — automatically, if you tell Git to.
✅
Summary Repository = project folder + full history of changes. Often shortened to just "repo". You'll create one for every project you work on.
🔄
Local vs Remote Repository
Your computer vs GitHub's servers
Local Repo

The copy of your project on your computer. You can edit files, commit changes — all without internet.

Remote Repo

The copy of your project on GitHub's servers. This is your backup and the version your team shares.

Like your phone and iCloud. Photos on your phone = local. Photos backed up to iCloud = remote. You work on your phone (local), then sync to the cloud (remote). If you lose your phone, your photos are still safe in the cloud.
✅
Summary Local = on your computer. Remote = on GitHub. You work locally, then push to remote to back up and share. You pull from remote to get the latest changes.

Day 2
Workflow — Clone, Commit, Push, Pull
Learning the core actions that power every Git workflow
⬇️
Clone
Download a repository from GitHub to your computer
What?

Cloning copies a repository from GitHub (remote) to your computer (local) — including all files and all history.

Why?

Before you can work on a project, you need it on your computer. Clone gets everything you need in one step.

When?

The very first time you start working on a project. You only clone once — then you pull to get updates.

Real World

Joining a new company? The first thing you do on day 1 is clone their repository to your new laptop.

📥
Clone = Downloading a shared project. Imagine your teacher puts a shared Google Doc online. Cloning is like downloading that document to your computer so you can edit it locally — but smarter, because it also brings the entire editing history.

How to clone with GitHub Desktop:

File → Clone Repository → Enter the GitHub URL → Click Clone. GitHub Desktop creates a local copy automatically.

How to clone with Git command line:

🖥️ Terminal
git clone https://github.com/username/my-first-repo.git
# This downloads the repo into a folder called "my-first-repo"
✅
Summary Clone = copy a repository from GitHub to your computer. You do this once per project. After that, use pull to get updates.
💾
Commit
Save a snapshot of your work with a meaningful message
What?

A commit is a saved snapshot of your project at a specific moment in time, with a message describing what changed.

Why?

It creates a point you can go back to. If something breaks, you can revert to the last good commit. Every commit is permanent history.

When?

Whenever you complete a small, meaningful task. "Added navbar", "Fixed login bug", "Updated footer". Think of it as press Save.

Real World

On large projects, hundreds of commits happen every day. Good commit messages are how teams communicate.

🎮
Commit = Saving your game. You wouldn't play a level without saving at the end. Committing is pressing the Save button in Git. Each save has a note: "Defeated the dragon on Level 3". Later, you can jump back to any save.

What a commit looks like in GitHub Desktop:

In GitHub Desktop, you'll see your changed files highlighted in green (added) and red (removed). Write a summary at the bottom and click "Commit to main".

How to commit with command line:

🖥️ Terminal — Making a commit
git add .          # Stage all changed files
git commit -m "Added navigation bar to homepage"

Good commit messages:

✅ Good Messages
  • Added responsive navbar
  • Fixed broken contact form button
  • Updated hero section colors
  • Removed unused CSS classes
❌ Bad Messages
  • stuff
  • changes
  • asdfasdf
  • fixed it
✅
Summary Commit = save a snapshot with a message. Do it often. Write clear messages. Each commit is permanent and can be revisited anytime. Small commits = better history.
⬆️
Push
Upload your commits from local to GitHub
What?

Push uploads your local commits to the remote repository on GitHub. It syncs your work to the cloud.

Why?

Commits live only on your computer until you push. Push = backup + sharing. Your team can't see your work until you push.

When?

After you make commits and are ready to share. In a team, push at the end of every work session at minimum.

Real World

Developers push their work before leaving office every day. It's the equivalent of "saving to the cloud".

📤
Push = Uploading to Google Drive. You can edit a document on your phone all day, but until you sync it to Google Drive, others can't see it and it's not backed up. Push is that sync button.
🖥️ Terminal
git push
# Uploads your commits to GitHub
# ✓ Branch 'main' set up to track remote branch 'main'.
✅
Summary Push = upload your saved commits to GitHub. Nothing is on GitHub until you push. Always push before you close your laptop for the day — your code will be safe in the cloud.
⬇️
Pull
Download the latest changes from GitHub to your computer
What?

Pull downloads the latest commits from GitHub (remote) to your computer (local). It updates your local copy.

Why?

When teammates push their work, your local copy gets out of date. Pull brings you up to speed with everyone's latest changes.

When?

Every time you sit down to work — before you start coding. Also when a teammate tells you they pushed changes.

Real World

A team of 5 developers — when one pushes a fix, the others pull to get it before continuing their work.

📥
Pull = Downloading the latest version. Imagine a shared Google Doc that your whole team edits. Pull is like clicking "refresh" to see everyone's latest edits before you start writing.
🖥️ Terminal
git pull
# Downloads and merges latest changes from GitHub
# ✓ Already up to date. (if nothing new)
💡 Golden rule: Always pull before you push, especially in a team. It prevents conflicts.
✅
Summary Pull = download latest changes from GitHub. Start every coding session with git pull. It's like checking for updates before you start work.
🌿
Branches
Work on new features without breaking the main project
What?

A branch is a parallel version of your project. You can add new features on a branch without affecting the main working version.

Why?

Imagine building a new feature that takes a week. If you break it, your main project is broken too. Branches prevent this.

When?

Whenever you start a new feature, fix a bug, or experiment. Don't work directly on main for anything beyond small edits.

Real World

Netflix engineers have hundreds of branches active at any moment — each team working on their own feature without disrupting others.

📓
Branch = Photocopying your notebook before an experiment. You make a copy of your notes, try a new approach in the copy. If it works, you replace your original. If it doesn't, you throw the copy away. Your original is always safe.

Branch Diagram

🌿 Branch Structure
main ← the stable, live version
feature/login ← you build the login here safely
feature/navbar ← teammate builds navbar here
← when done, both merge back into main

Types of Branches:

Branch TypePurposeExample Name
mainThe stable, production-ready version. Always working.main
feature/Building a new feature safelyfeature/login-page
fix/Fixing a specific bugfix/navbar-mobile
experiment/Trying something new — might deleteexperiment/new-design
✅
Summary Branches let you work in parallel. Main is always stable. You build features on separate branches, then merge them in when they're ready. This is how real teams work.
🔀
Merge (Introduction)
Bringing a branch's changes back into main
What?

Merge combines the changes from one branch into another — usually from a feature branch back into main.

Why?

When your feature is done and tested, you merge it into main so everyone gets the new feature.

When?

After you've finished working on a feature branch and tested it thoroughly. Never merge broken code into main!

Real World

On GitHub, teams use "Pull Requests" to review code before merging. Someone else checks your work first.

📓
Merge = Copying your experiment notes back into your original notebook. You photocopied your notebook (branch), made changes, verified they work, then wrote those changes back into the original (merged into main).
We'll explore merges in more depth as you get comfortable with branches. For now, understand that merge = combine branches together.
✅
Summary Merge = take changes from one branch and apply them to another. Feature branch → merge into main → everyone gets the feature. This is the core loop of professional development.

Day 3
Git CLI & VS Code
Learning the terminal commands that professionals use every day
🔵
Git in VS Code
Built-in version control panel inside your code editor
What?

VS Code has Git built in. Click the branch icon (third icon in the left sidebar) to see all your changed files, stage them, and commit — without leaving your editor.

Why?

It's faster than switching apps. You can see your code changes and commit them in the same window, side by side.

When?

When you're coding in VS Code and want to commit without opening a separate app or terminal.

Real World

Most professional developers use VS Code's built-in Git or use the terminal. GitHub Desktop is great for beginners but professionals prefer staying in the editor.

VS Code vs GitHub Desktop

🖥️ GitHub Desktop
  • Separate, dedicated app
  • Cleaner, more visual interface
  • Best for beginners
  • Easy to see file history
  • Great for managing multiple repos
🔵 VS Code Git
  • Built into your code editor
  • Never leave VS Code
  • See code changes and commit together
  • Faster workflow once you know it
  • Most popular professional choice
✅
Summary Both tools do the same Git actions. GitHub Desktop is visual and great for starting out. VS Code's built-in Git is faster for daily use. Learn both and choose what works for you.
⌨️
Git Commands — The Essential Six
Every command you need for daily development work

These 6 commands cover 90% of everything you'll do with Git every day. Master these first.

1. git clone

Download a repository from GitHub to your computer. Use this once per project.

git clone
git clone https://github.com/username/project-name.git
# Creates a folder called "project-name" with all files + history

2. git status

Check what files have changed since your last commit. Your most-used command!

git status
git status
# Shows you which files are changed, staged, or untracked
# Run this before every commit to see what you're about to save

On branch main
Changes not staged for commit:
        modified:   index.html
        modified:   style.css

3. git add .

Stage all changed files, preparing them to be committed. The dot . means "everything".

git add
git add .           # Stage ALL changed files
git add index.html  # Stage one specific file only
# "Staging" = marking files as "ready to be saved"

4. git commit -m ""

Save a snapshot of your staged files with a message describing the change.

git commit
git commit -m "Added login page with email and password fields"
# -m means "message" — write what you changed
# [main a3c5d18] Added login page with email and password fields
# 2 files changed, 47 insertions(+)

5. git push

Upload your commits from your computer to GitHub. Share your work with the world.

git push
git push
# Uploads commits to GitHub
git push origin feature/login  # Push a specific branch

6. git pull

Download the latest changes from GitHub to your computer. Always do this before starting work.

git pull
git pull
# Downloads and applies latest changes from GitHub
# Fast-forward → your files are now up to date

The Daily Git Workflow
The exact sequence you'll follow every single day
🔁 Complete Git Workflow
1. git pull
2. Edit Files (write code)
3. git status
4. git add .
5. git commit -m "Your message"
6. git push
✓ Done! Repeat tomorrow.

Full workflow example — building a contact page:

🖥️ Complete Session
# Step 1: Get the latest code before starting
git pull

# ... you build the contact page in your editor ...

# Step 2: See what you changed
git status

# Step 3: Stage all your changes
git add .

# Step 4: Save a snapshot with a description
git commit -m "Added contact page with form and map"

# Step 5: Upload to GitHub
git push

# ✓ Your work is saved, backed up, and visible to your team.
✅
Summary — The Golden Sequence Pull → Code → Status → Add → Commit → Push. Memorize this. Do it every single session. Even experienced engineers follow this exact loop every day.
📝 Homework — Day 3 (Independent Practice)
  • Open your project in VS Code
  • Open the VS Code terminal — View → Terminal (or Ctrl + `)
  • Run git pull to get the latest changes
  • Add a new page (e.g., projects.html) — build it out
  • Run git status to see your changes
  • Run git add . to stage everything
  • Run git commit -m "Added projects page"
  • Run git push to upload to GitHub
  • Verify it appears on github.com/your-username/your-repo
  • Repeat — Do the full workflow 2 more times independently
